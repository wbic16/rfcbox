## Rules mapping (Orion's five points → the skill)
1. **Exactly one status + basis + evidence pointer per entry.** Skill: a status is never bare; every registry entry carries basis + evidence pointer; basis constrains status per the table (STIPULATION/VERIFIED→True, REFUTED→False, ATTRIBUTED/OPEN/SYNTHESIS/ESTIMATE→Unknown, CONSTRUCTION→Fiction). Audit method: full-population programmatic check over ietf-source.json — count entries, verify exactly one status and one basis each, evidence pointer non-empty, every (basis,status) pair in the allowed table. Any violation = defect by definition.
2. **Supersession sample.** Skill: no pruning — retirement is relocation with redirect; False is for REFUTED claims, and obsolescence is not refutation (see point 5). Audit method: deterministic sample of 20 obsoleted RFCs (every nth from the source list); each must be (a) present in full — scroll length consistent with the fetched text / hash on record, (b) annotated with its obsoleted-by receipt, (c) carrying a redirect to the successor's coordinate. One miss fails the sample.
3. **No pruning / totality.** Audit method: scroll count vs rfc-index total from the builder's own index fetch; every indexed RFC has exactly one scroll (totality + uniqueness, the Lean Accurate conditions applied to the corpus); text-unavailable RFCs present as annotated scrolls, not absent.
4. **Priority tiers.** Audit method: the tier overrides table must exist as explicit data (in source or builder), reviewable entry-by-entry; spot-check that tier correlates with organization/index order only, and that Tier 3 entries are complete scrolls, not stubs (compare a sample of Tier 3 scroll lengths/hashes against fetch records).
5. **The classification decision — pre-judged against the skill, to be confirmed on the landed data.**
   - Bibliographic record → True/VERIFIED is the skill's OWN default ("bibliographic records → True/VERIFIED (checked against the source at ingestion)"). Sound, PROVIDED the ingestion check is real: index metadata cross-checked at fetch and the SHA-256 of the fetched text recorded as the receipt/evidence pointer. If entries claim VERIFIED without a recorded hash or source URL, that leg fails.
   - Supersession as annotation/redirect (not False/REFUTED) is CORRECT, not a fudge: an obsoleted RFC has not been refuted — its successor relation is itself a bibliographic fact (True/VERIFIED against the index), and the MVO retirement rule is exactly "relocation with a redirect, history and receipts reachable." Marking thousands of obsoleted RFCs False would corrupt the registry's meaning of False.
   - The one overreach to hunt at audit: the VERIFIED status covers the RECORD (this RFC exists, this is its text, this is its status in the index). It must not silently extend to the RFC's normative claims — those are the source's assertions (ATTRIBUTED territory). If any entry or index prose presents the contents as established-by-us, that's a defect. Likewise text-unavailable entries: the record is VERIFIED from the index; the absent text must be annotated as absent, never implied held.

## Extension leg — canonical implementations (added 2026-11-18 09:17 CST, Will via Orion)
Per-RFC canonical open-source implementation links, carried for later algorithmic composition with phcc. Audit mechanics:
6. **Basis + evidence on implementation records.** Each implementation record carries status/basis/evidence like every other entry. VERIFIED only where the builder actually checked (a) the repo exists and (b) the project itself names the RFC; anything less is ATTRIBUTED/Unknown. Audit: sample implementation records across tiers (all Tier 1 records in the sample set), resolve each evidence pointer to the project source and confirm the RFC is named there. A canonical claim with no evidence pointer fails this leg outright.
7. **Explicit none-state.** Full-population check: the implementation field is never silently empty — every RFC carries either ≥1 implementation record or an explicit "no canonical implementation identified" state. Silently empty = defect; an invented mapping (record whose project does not name the RFC) = worse defect, fails the leg.
8. **License on every record.** Full-population check: license field present and non-empty on every implementation record (the phcc composition step needs license clarity). Missing license = a recorded finding, enumerated by coordinate; any Tier 1 record missing a license blocks READY.
9. **Co-canonical ecosystems.** Review Tier 1 assignments plus known multi-implementation standards: where the ecosystem plainly has co-canonical implementations and the build forced a single winner, flag it as a judgement defect for Will's correction via the overrides table. These are listed in the verdict as required corrections — they are judgement defects, not bookkeeping failures, and do not by themselves flip the verdict unless a Tier 1 mapping is plainly wrong.

## Extension leg 2 — dependency graph for RFC Box (added 2026-11-18 09:20 CST, Will via Orion)
RFC Box (task 34.5.9/7.6.10/6.5.9) will read the dependency graph from ietf.phext's coordinate space. The build captures per-RFC edges: index edges (obsoletes / obsoleted-by / updates / updated-by), normative/informative reference edges extracted from each RFC's References section, and the implementation edges (points 6–9). The audit covers the graph, not the RFC Box program.
10. **Edges are record-facts.** VERIFIED basis requires the edge be traceable to the index entry or the citing text. Audit: sample 10 normative reference edges across eras (early / mid / modern), resolve each against the citing RFC's actual References section in the shipped scroll. An edge that isn't in the cited text fails; a pattern of them fails the leg.
11. **Honest incompleteness.** RFCs whose references couldn't be parsed must carry extraction: "unparsed" as an explicit state. A silent empty edge list on an RFC that plainly cites others is a defect (same family as point 7's silently-empty implementation field). Audit: reconcile the builder's parsed/unparsed counts by era for plausibility — early RFCs should fail parsing more; a uniform ~100% parse rate across eras is a red flag, not a success, and triggers a deeper sample.
12. **Reverse walkability.** Pick 3 well-known RFCs and verify the reverse direction ("what needs this" — updated-by / cited-by / implemented-by) resolves from the shipped data structures alone, with no rebuild or external lookup. If reverse edges exist only as forward edges that a reader must invert by scanning the whole corpus, that's a finding against RFC Box readiness (the graph is its data model).
